## 3. تغييرات البيئة والتشغيل (Environment / operations)

### متغيرات جديدة في نموذج متغيرات البيئة

أضيفت المتغيرات التالية إلى ملف نموذج متغيرات البيئة (example env):

| المتغير | القيمة الافتراضية | الوصف |
|---|---|---|
| `DATABASE_HOST_PORT` | `5433` | منفذ قاعدة البيانات على المضيف (host) فقط، يُستخدم في `docker-compose.yml` لتوجيه المنفذ المنشور. |
| `JWT_SECRET_KEY` | (بدون قيمة افتراضية) | مفتاح توقيع JWT. إلزامي وغير قابل للافتراض. |
| `APP_ENV` | `development` | بيئة التشغيل (`development` / `test` / `production`). |
| `CORS_ORIGINS` | `http://localhost:5173` | أصول مسموحة مفصولة بفواصل. |
| `SQL_ECHO` | `false` | طباعة استعلامات SQL في السجل. |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` / `SMTP_PASSWORD` / `SMTP_FROM` | فارغة / `587` | إعدادات إرسال رمز التحقق عبر البريد. |

### تصحيح سبب فشل الاتصال بقاعدة البيانات

- سابقاً كان الـ compose يبني `DATABASE_URL` بالاعتماد على `DATABASE_PORT` (وهي قيمة المضيف `5433`)، فيحاول الـ container الوصول إلى `db:5433` ويفشل.
- الآن داخل شبكة compose يستخدم الباك إند دائماً `db:5432`.
- `DATABASE_HOST` و `DATABASE_PORT` صارا مخصَّصين فقط لتشغيل الباك إند **خارج** Docker عبر المنفذ المنشور (اختياري).

### ما يجب على كل زميل فعله بعد سحب `dev`

1. حدّث ملف متغيرات البيئة المحلي من النموذج، وعبّئ القيم، وأهمها `JWT_SECRET_KEY` (استخدم مثلاً `openssl rand -hex 32`). لن يعمل الباك إند بدون مفتاح صالح.
2. أعد بناء وتشغيل الحزم: `docker compose up --build`.
3. تأكد من `GET /health` يعيد 200.
4. أنشئ حساب المدير (مرة واحدة فقط): انظر القسم 5 والأوامر أدناه.

### أوامر جديدة

```bash
# إنشاء حساب المدير (يطلب كلمة السر مرتين عبر getpass)
docker compose exec back python -m scripts.create_admin --username admin

# إعادة تعيين كلمة سر المدير الحالي
docker compose exec back python -m scripts.create_admin --username admin --reset-password
```

- كلمة سر المدير: 12 محرفاً على الأقل.
- السكربت يرفض إنشاء مدير ثانٍ (SRS FR-13)، ويخرج برمز غير صفري.
- لا يوجد أي endpoint HTTP لإنشاء المديرين.

## 4. تغييرات السلوك (Behaviour changes)

- **تسجيل دخول المدير**: كان يقارن كلمة السر نصاً صريحاً مع المخزَّن. الآن يستخدم `bcrypt` عبر `verify_password`، ويجري فحص bcrypt وهمياً للمستخدم المجهول حتى لا يكشف توقيت الاستجابة وجود اسم المستخدم.
- **مفتاح JWT**: مصدر واحد في `app/core/security.py`. القراءة من `JWT_SECRET_KEY`؛ الفراغ/المسافات/أقل من 32 محرفاً تُعتبر غير موجودة وترفع `RuntimeError` عند الاستيراد. لا توجد قيمة افتراضية. الرموز: رمز التسجيل يحمل `purpose="registration"` و`decode_registration_token` يرفض أي رمز لا يحمله.
- **CORS**: أُضيفت `CORSMiddleware`؛ `allow_credentials=False` (لأننا نستخدم Bearer)، والأساليب والرؤوس هي المستخدمة فعلياً فقط.
- **SQL echo**: صار مقاداً من `SQL_ECHO` (افتراضياً false) بدل تشغيله دائماً.

## 5. كيفية تشغيل الاختبارات

```bash
docker compose exec back sh -c "pip install -r requirements-dev.txt && pytest -q"
```

- قاعدة بيانات الاختبار `graduation_test` وقاعدة Redis رقم 15، معزولتان تماماً عن بيانات التطوير. يوجد حاجز يمنع تشغيل الاختبارات على قاعدة بيانات لا ينتهي اسمها بـ `_test`.
- إعدادات التوافق: `asyncio_mode = auto`، وحلقة حدث واحدة لكل الجلسة (session) (ضروري لـ asyncpg و Redis).

## 6. القرارات (D1–D8)

- **D1**: Redis يبقى (تحديد المعدل، قائمة الرموز الملغاة، الـ cache). مقبول من المالك ولا يُزال.
- **D2**: دلالات QR تتبع نموذج السير: العمود `is_activated` يعني «مسموح له بالمسح»، والتوابع تصبح مفعَّلة بعد مسح رمز الخريج. لا إعادة تسمية ولا أعمدة جديدة (يُنفَّذ في المرحلة 2).
- **D3**: لا يكشف أي endpoint إن كان الرقم الجامعي أو البريد مسجلاً؛ الرسائل عامة (يُنفَّذ في المرحلة 1).
- **D4**: سياسة كلمة السر: 8 أحرف على الأقل، حرف ورقم على الأقل، 72 بايت UTF-8 كحد أقصى (يُنفَّذ في المرحلة 1).
- **D5**: `revert_scan` يعيد مسح الخريج وكل المرافقين ويُلغي تفعيل رموز المرافقين (يُنفَّذ في المرحلة 2).
- **D6**: سلوك Redis عند الفشل: فحص قائمة الرموز الملغاة يفشل مغلقاً (503)، ومحدِّدات المعدل تفشل مفتوحة مع تسجيل WARNING (يُنفَّذ في المرحلة 1).
- **D7**: كل رسالة للمستخدم عربية فقط، وتُوضع الرسائل الجديدة في `app/core/messages.py` (يُنفَّذ في المرحلة 1).
- **D8**: تغييرات عقد الـ API مسموحة الآن لعدم ربط الواجهة بعد، وتُوثَّق هنا وفي التقارير.
